# Aether Brain — product spec (trimmed working copy)

## 0. Product definition

Aether Brain is a personal knowledge operating system whose primary interface is a navigable 3D thought-space, not a file tree.

- A note is a neuron.
- A `[[wikilink]]` is a synapse.
- A folder / PARA area is a cluster / constellation.
- A tag is a colored field.
- Time is an orbital layer.
- In the **system layout** the folder tree is a set of solar systems: the vault (or each drive) is a sun, a project's home folder is a star, folders are planets, notes are moons.
- Capture, edit, search and wander all happen inside or beside that space.
- Claude and ChatGPT can talk to the brain directly through a local MCP server (the **AI link**).

**Not:** an Obsidian plugin, a 2D graph with a 3D camera bolted on, a chat wrapper around notes, a SaaS that uploads the vault.

**Is:** a standalone app the user runs locally; markdown files on disk as the source of truth; a cinematic, usable 3D knowledge world; a real second brain loop — Inbox → organize → connect → retrieve → review.

Aesthetic: dark cosmos / living neural map. Deep space, bloom, glowing nodes, filament edges, readable UI chrome.

## 1. Hard constraints

- TypeScript strict throughout.
- Local-first. No required cloud account. No telemetry.
- Notes live as `.md` files in a user-selected vault folder.
- Wikilinks: `[[Note Title]]`, `[[Note Title|alias]]`, `[[Note Title#heading]]`, `![[Note Title]]` (embed).
- Frontmatter YAML: `title, tags, created, updated, status, area, type, aliases`.
- No proprietary note format.
- Graph physics never blocks the main thread: Web Worker (`d3-force-3d`).
- No secrets committed, no analytics SDKs.
- Fewer dependencies over a zoo of libraries.
- Every feature has a keyboard path (see KEYBOARD.md).
- 60 fps on a mid laptop at 1,000 nodes / 2,500 edges: instanced meshes, one draw call per primitive type.
- If a library fights the product, write the piece.

## 2. Stack

Electron 44 (desktop shell, folder picker, native recursive `fs.watch`) · Vite 8 + React 19 + TypeScript · Zustand · Tailwind v4 + CSS tokens · three + @react-three/fiber + drei · d3-force-3d in a worker · postprocessing bloom (selective) · unified/remark-parse/remark-gfm + js-yaml + custom wikilink tokenizer · react-markdown preview with wikilink rendering · MiniSearch · pnpm, Node 22+.

AI link: `@modelcontextprotocol/sdk` + zod, bundled into one ES module (`dist/mcp/aether-mcp.mjs`) that the app runs in-process (HTTP) and Claude Desktop runs over stdio.

Deferred (not MVP): SQLite FTS, AI embeddings / chat inside the app, WebXR.

## 4. Data model (`packages/core/src/types.ts`)

```ts
type NoteId = string // stable: relative path without .md, posix
type NoteType = 'note' | 'daily' | 'person' | 'project' | 'area' | 'resource' | 'inbox' | 'concept' | 'moc' | 'board'
type Area = 'inbox' | 'projects' | 'areas' | 'resources' | 'archive' | 'untagged'

interface NoteMeta {
  id: NoteId; title: string; path: string; folder: string
  area: Area; type: NoteType; tags: string[]
  created: string | null; updated: string | null; status: string | null
  wordCount: number; headings: { depth; text; slug }[]; aliases: string[]
}

interface Link { from: NoteId; to: NoteId; raw: string; kind: 'wikilink' | 'embed' | 'tag'; heading?; alias?; resolved: boolean; offset: number }
```

Derived: `title` = frontmatter.title → first H1 → filename. `area` = frontmatter.area → top folder (PARA names, numeric prefixes tolerated) → `untagged`. `type` = frontmatter.type → nearest folder (`Daily`, `People`, `Maps`, …) → `daily` if the filename is a date → `inbox` if in the inbox → `note`.

Link resolution order: exact path/id → title → alias → filename (unique, else shortest path). Unresolved targets become **ghost** nodes (`ghost:<target>`) so missing notes are visible and creatable.

Graph (`buildGraph`): nodes (notes + ghosts, deterministic order), weighted edges collapsed per (from, to, kind), backlinks/outlinks maps, orphans, tag and area counts. Every node has a `kind` (`note` · `ghost` · `folder` · `image` · `today`) and a structural `parent`.

**Pictures** (`vault/assets.ts`): png, jpg, jpeg, webp, gif, bmp and avif files are the vault's pictures (SVG is left out: it can carry scripts). `![[gate.png]]` and `[[gate.png]]` resolve Obsidian-style (exact path → path relative to the note → nearest file of that name) to `image:<path>` nodes with an edge from the note; a picture link that resolves to nothing stays unresolved and never becomes a ghost. In the system layout each shown folder also gets its newest pictures as moons (24 per folder, linked ones included; 1,500 picture nodes at most), and folder nodes count `images` / `shownImages`.

**Tasks and the daily brief** (`markdown/tasks.ts`, `markdown/brief.ts`): a task may carry a due date (`📅 2026-10-01`, `🗓 …`, `[due:: …]`, `@due(…)`, `due:…`), a scheduled date (`⏳ …`, `[scheduled:: …]`) and inline `#tags`. `dailyBrief` gathers every open task that is overdue, due today, scheduled for today or earlier, in today's daily note, or tagged `#today` (Archive excluded; each task once), plus the first open task of every active project with nothing above ("next up"). It is derived and never written. With `today: { brief }` the graph gets one **Today hub** (`today:`), appended last, whose beams (`EdgeKind 'today'`) go to the notes of the brief; the beams are the hub's outlinks only, never a note's backlinks.

**Critiques** (`markdown/critique.ts`): a graded drawing is a PNG plus a note next to it: `critiqueNote` writes `![[<file>.png]]`, the grade as text and as Dataview inline fields (`grade:: B+`, `score:: 82`), a scores table, the fixes as tasks (the first one due tomorrow when asked: tomorrow's brief), what's working, and the deep critique quoted. No new frontmatter keys; tags `critique`, `concept-forge`, `drill/<name>`. `normalizeGrade` reads grade objects of any common shape.

Built with folders (`buildGraph(notes, { folders })`, the system layout only), the graph also gets one node per visible folder (`folder:<path>`, the root is `folder:`), appended after the ghosts. `selectFolders` picks them: the root, every drive (mount) of a multi-root vault, every folder that holds notes, project folders, the children of expanded folders, then a breadth-first sweep down to the depth limit (default 3) up to 1,500 optional folders — a whole drive can hold hundreds of thousands. Folder roles: `root` (the vault), `mount` (a drive such as `D:\`), `project` (a folder bound to a project note: a star), `folder` (a planet). Parents: folder → nearest visible ancestor; note → its project's folder when it is the project note, else its nearest visible folder; ghost → the first note linking to it. Folder nodes add no edges, backlinks, tag or area counts.

**Projects** (`markdown/projects.ts`): a project is a note with `type: project`, a note directly in a Projects folder (`Projects/X.md`, `D/Projects/X.md`), or the folder note of a direct child (`Projects/X/X.md`) — never a note in Archive, never an ordinary note deeper inside a project folder (`isProjectNote`; `meta.type` says `project` for everything under Projects and is not the test). Its home folder (`projectFolderOf`): frontmatter `folder:` → the folder it is the folder note of → a same-named sibling folder (`Projects/PORTALz.md` + `Projects/PORTALz/`). `setProjectFields` rewrites title (old title kept in `aliases`), status, summary (the `>` line under the H1), tags and folder, leaving the rest of the file byte-identical, and refuses frontmatter whose YAML does not parse. Tasks are edited, deleted and moved in place (`editTask`, `deleteTask`, `moveTask`).

**Multi-root vaults**: a vault can span several folders or whole drives. With more than one root every vault path starts with the root's mount (`D/Projects/x.md` is `D:\Projects\x.md`); with one root paths are relative to it, as before. New notes (capture, daily, ghosts, projects) go under the first root (`homePrefix`); moving a note to a PARA area keeps it on its own drive.

## 5. Views

`graph | editor | capture | search | review | projects | boards` — a tiny state machine in the store, not routes. The graph is always mounted; the other views float over or beside it. The two that fill the window with a panel, the Projects board and the Boards view (`FULL_PANEL_VIEWS` in the store), stop the 3D view drawing while they are up (`BrainController.setCovered`, driven from the view by one effect in `App.tsx`; the scene's frame loop is `frameloopFor` in `packages/graph/src/scene/frameloop.ts`; the layout keeps running) and use a solid panel (`.panel-solid`, no backdrop blur). Review and quick capture are small dialogs over a scene that stays alive. The top bar fits one line from 1100 px (the key hints, the brand name and the search button give way as the window narrows, `topbar-wide` / `topbar-roomy` in `styles.css`).

- **Graph**: instanced neurons + halos, filament synapses with travelling pulses on the focus, starfield + nebula, selective bloom, label overlay, screen-space picking, drag-to-pin, fit-to-graph camera, color by area / type / tag / age, tag field sphere. Three layouts (`t` cycles): **constellation** (force layout clustered by area), **orbit** (force layout, age as rings) and **system** (the default): the folder tree laid out analytically as nested solar systems — no physics; children orbit their parent on tilted rings (many leaf moons form a sphere shell), planets keep moving while orbit motion is on (`o`) and the camera follows the selected one. Stars (project folders) and suns (the vault, drives) bloom; planets take a stable colour from their path; orbit rings are drawn for every system, brighter around the selection. Depth `[` `]`, expand `x`, double-click a folder to expand it. Only system graphs carry folder nodes: switching layout, depth or expansion rebuilds the graph, and folder changes on disk arrive live (`addDir` / `unlinkDir`).
- **Folder inspector**: a selected folder shows its role, path, note, folder and picture counts, its planets, moons and pictures, and actions — new note / new folder here, import pictures, make it a project (writes its folder note) or open its board, expand / collapse, reveal on disk (desktop).
- **Today** (`y` · `7`, the ☀ chip): selects the hub; the inspector lists Overdue / Today / Next up with a tick box per task (writes `✅` into the task's own note; `u` undoes), the project chip (flies to its star) and the note. A picture moon shows the picture framed; picture thumbnails come from the adapter (`thumbnail(path, size)`), the 256 nearest on screen, in one texture array of 256 px layers. **Picture size** (`z`, the legend's M · L · XL, `settings.pictureSize`): medium, large (default) or extra large icons, a picture radius of 1.4, 3.2 or 5.5 (`PICTURE_RADIUS`, through `nodeRadius`); the system layout reserves each picture's drawn width (2.4 radii), so orbits widen and pictures never overlap; a change rebuilds the graph and the camera follows the selection once the layout settles (else refits).
- **Star galleries** (system layout): when the camera and the point it looks at both come within 2.6 system radii of a project star (measured where the camera is headed, once it has stayed there 0.3 s and not during the first framing flight; of several, the star looked at most closely; hysteresis: it folds past 3.4, and another star takes over only when it is looked at 15 % more closely), the store rebuilds the graph with `images.gallery = <star folder>`: every picture under the folder, subfolders included, newest first, becomes a card (`ImageNodeInfo.gallery`; moons and linked pictures keep their node and orbit slot, the rest come in parented to the star, at most 480). The layout puts the cards on an upright Fibonacci sphere around the star, just clear of its system, taking no room in any system, so nothing else moves; the worker sends each card's size with the rings. Cards grow out of the star (0.9 s) and shrink back before the graph lets them go (0.42 s); a card wider than 40 % of the view fades out and lets clicks through (unless selected). `⇧ G` opens the gallery of the selection's star (else the nearest) and flies there, or folds the open one (it then stays shut until the camera leaves that star); *Toggle star galleries* (palette) turns the fly-close opening off. The folder inspector of a star has *Gallery · N* / *Fold gallery*.
- **Picture inspector**: preview (a video: its still, with a ▶ badge), folder, size, date, open in the OS image app or video player (`e`, desktop), reveal, copy the `![[embed]]`, *Add to board* (a picture only: a menu of the newest boards and a new one, §13), and the notes that embed it.
- **Videos** (mp4, m4v, mov, webm; no Ogg Theora, which Chromium does not decode) are media like pictures (`isMediaPath`: listed, watched, linked with `![[clip.mp4]]`, moons, gallery cards; `ImageNodeInfo.video`), shown as one still frame — a tenth of the way in, at most 5 s — with a ▶ badge (the card shader, the inspector, note embeds), never played in the brain; `e` plays one in the OS player (desktop: `openAsset` checks the file starts like a video). Desktop: main reads only a video's first bytes (its signature: ISO BMFF with a real box after any filler box, fragmented MP4, Matroska, and MPEG-TS, which only the OS player plays) and hands the thumbnail helper a one-job address (`aether-video://clip/<token>`, a privileged streamable scheme served on the helper's session from that file in byte ranges, CORS-readable, 404 once the job ends, when any stream still open ends too); the helper's media player seeks and draws the frame. The watcher reports a known video that is still being written (recorded, copied in) once it has been left alone for 4 s, not on every write. Browser adapters hand the video itself to the store, which takes the still (`stillOf` / `videoStill`: three at a time, kept per path, size and file version). A still that comes out see-through (`seeked` a moment before the frame can be drawn) is drawn again, then kept when the video has its frame (a transparent background). Imports stay pictures only. Pictures dropped on the window (or picked with *Import pictures…*) are copied into the selected folder, the selected project's Critique planet, or the Inbox — create-only.
- **A crash while opening never loops**: if the window dies while a vault is opening (or within a minute of it), the next start does not reopen those folders by itself. The welcome screen says what happened (the page's memory, what the vault held, where the crash report is) and offers the same folders without pictures and videos, the same folders again, or other folders. A failed layout (its worker threw) is told in a message instead of leaving every body at the origin.
- **Editor**: raw markdown + live preview (split / edit / preview), `[[` autocomplete, autosave (900 ms) + `⌘S`, rename via title, `updated:` touched on save. **Long notes are bounded** (v0.9.1, `preview.ts`): laying text out costs memory in proportion to its length (an imported chat of 1 MB took about 1 GB, one of 16 MB about 10 GB, and the window died with *ran out of memory*; the editor's text box alone is about half a gigabyte per MB, two page elements per line), so the preview draws the first 60,000 characters of a note (cut at a paragraph, an open code block closed), 60,000 more per *Show more* up to 300,000 (a note embedded in another: 20,000, no button), and a note over 400,000 characters opens read-only as that preview, with no text box and a notice that the file is untouched. The Review queue's preview is the same component. **Loading is bounded too** (v0.10.0, `parseNote`): reading markdown costs about 1.2 s and 300 MB of memory for every MB (a 3 MB chat peaked above half a gigabyte, one huge list or quote takes quadratic time, and a 12 MB chat ran the window out of memory *while the vault was loading*: the user saw one star, everything clumped, then the crash), so a note is read as markdown only up to its first 120,000 characters (cut at a blank line): its links, tags and headings come from there, its search text goes on to 250,000 characters, its word count is the whole note's, and the Inspector says *Long note*; an imported chat is read only up to 40,000 characters (its text is inert). The notes cross from main to the window a page at a time (12 MB a page; a vault of 300 MB of chats used to kill the whole app in one oversized reply), the search text is indexed in slices so the window keeps answering, and a note file over 64 MB is left on disk and not loaded. The note itself, its file and its editor are untouched.
- **Capture**: one box → `Inbox/<title>.md` with frontmatter (`type: inbox`, `status: unprocessed`).
- **Search**: palette over title / aliases / headings / tags / body / path; `>` for commands; `⌘Enter` converts a query to a graph filter; `is:orphan`, `is:stale` pseudo-queries.
- **Review**: queue = unprocessed inbox → orphans → spaced-review due → stale (>90 days). Actions move files between PARA folders and patch frontmatter; review intervals live in localStorage.
- **Projects**: board of every project note (`isProjectNote`) with progress from its markdown task list. Everything is editable in place and written straight back into the note: the name (`e`; the file follows — `Projects/Old.md` → `Projects/New.md` unless it is a folder note — and the old name stays an alias), status (select, `s` cycles active → paused → done → someday), tags, and summary; the **home folder** row shows the project's star folder with *Show in space*, *Change…* (searchable folder picker, writes `folder:`), *Unlink*, or *Create folder* / *Link existing…*; the **planets** are its subfolders with note counts, and *Add folder* (`f`) creates `<home>/<name>` on disk (the home folder first when needed). Tasks: tick (`- [x] … ✅ YYYY-MM-DD`, Obsidian Tasks convention), add under `## To do`, edit (✎, double-click, `Enter`), move (`Alt ↑↓`, ▲▼), delete (✕ / `Del`, with Undo). *Archive* moves the note to `Archive/`, *Delete…* asks first; a project's folder always stays on disk. "New project" scaffolds `Projects/<name>.md`. The note is the memory — no side database. A task's `[[links]]` are resolved with one index of the notes for the whole board, built the first time a task has a link (a row of its own would build one per task: a long to-do list in a big vault used to freeze the window and fill the memory).
  **Nothing the board draws is unbounded** (v0.8.4): every element is a DOM node and a React fiber (3 to 5 KB), so 20,000 project cards, 100,000 tasks or 100,000 folder chips drawn whole took 2 to 10 GB and killed the window. The project cards are windowed (fixed height, only those in view exist, two spacers keep the scroll bar; `j` / `k` scroll the selection into view; `windowing.ts`, `ProjectCardList.tsx`); the to-do and done lists are drawn 200 tasks at a time (*Show more* or `m`, one page per press; a task that must take focus, after a move or an edit, draws the list down to it) and never more than 2,000 (the board says how many more are in the note), the folder chips 48 at a time (*+N more*) and never more than 2,000; a task draws at most 40 links and tags as links; titles, paths, tags (40), task texts (2,000 characters), heading labels (40) and summaries are cut; the link scan of a task is linear. The board is a wrapper that renders nothing, and does none of its work (project list, folder maps, note counts), while it is closed. The notes under each folder are counted once per change of the notes, not once per project. What was typed on the board (a half-written task, project or folder name, the open Done list) lives in the wrapper, so closing the board loses none of it.
- **Boards** (`8` · `⇧ B`): the vault's reference boards (§13): a list of cards with a collage of each board's pictures, and a board opened full size. Like the Projects board it is a wrapper that does nothing while closed, draws a page of cards at a time and loads the pictures only for the cards in view. While a board is open it owns the keyboard (the 3D view's single keys do not fire behind it).
- **When a part of the app crashes** while drawing, it shows a notice in its place (what broke, the error to copy, *Close* · `Esc`, *Try again*) and the rest of the window stays (`ErrorBoundary` around the scene, the top bar, the editor, the inspector and every overlay and panel; the small pieces of chrome draw nothing). A page that dies altogether (out of memory) is opened again by the desktop app with a message saying why, unless it keeps dying (`src/main/crash.ts`).

## 6. Vault adapters

`VaultAdapter { list, read, write, create?, remove, rename, watch, roots?, listFolders?, createFolder?, reveal?, listAssets?, thumbnail?, readAsset?, createAsset?, openAsset? }` implemented by `MemoryVaultAdapter` (demo + tests; the demo keeps edits and folders made in the app in IndexedDB), `FsAccessVaultAdapter` (browser folder, polling for files and folders), `ElectronVaultAdapter` (IPC to a path-jailed main process: `FsVault` scans one or more roots breadth-first — hidden, system and heavy folders such as `Windows`, `Program Files`, `node_modules`, `.git` skipped, and so are game libraries and folders that hold an installed game or program (`installs.ts`: store and engine marker files, uninstallers, an `.exe` with its DLLs; `keep` shows one anyway) and folders the user left out (`hidden`, absolute paths; `⇧ H`, applied live: the watcher unlinks what was shown and walks a folder let back in) — and writes atomically; `VaultWatcher` uses native recursive `fs.watch` per root with a 250 ms debounce and self-write echo suppression, and reports folders as `addDir` / `unlinkDir`). The desktop app can open several folders or whole drives at once (vault folders panel, `v`).

## 7. AI link (desktop)

Claude and ChatGPT talk to the brain directly through a local MCP server (`apps/desktop/src/mcp`): search and fetch (the ChatGPT connector convention), overview, read notes with backlinks and tasks, list folders as a tree, projects and their planets, related and recent notes, and — unless the link is read-only — create notes, append, edit, update frontmatter, capture, tasks, projects and folders. No tool deletes a note; every write goes through the same path-jailed `FsVault` and only writes `.md` notes. Claude Desktop runs it over stdio (a one-click `.mcpb` bundle); ChatGPT and claude.ai reach the in-app HTTP link (`127.0.0.1` only, secret token in the URL or a Bearer header) through a tunnel. AI edits show up live as toasts and the camera flies to what was touched. Panel: `a`. Setup: [AI-LINK.md](AI-LINK.md).

## 8. Concept Forge link (desktop)

`g` opens the user's own `concept-forge.html` (picked once, remembered) in a window of its own session (`persist:forge`, so the page's own online features keep working while the brain stays offline). A preload exposes only `window.aetherForge` (`projects()`, `save()`) and injects a **🪐 Save to Brain** button (`Ctrl+Shift+B`) in a closed shadow root: it captures the drawing canvas (overlays left out), reads the page's grade (`lastGrade`, or its grade history in localStorage), and asks for the project and title. Main validates the save (PNG signature, 40 MB, JSON-safe grade ≤ 256 KB) and relays it to the brain window, whose store writes the PNG and the critique note create-only into `<project home>/Critique/`. Setup and details: [FORGE-LINK.md](FORGE-LINK.md).

**The Concept Forge star** (v0.8). The project star that carries the Forge (`renderer/forge-star.ts`: the project named Concept Forge by folder, title or alias, the one holding the page first; else the deepest project star holding `concept-forge.html`) gets a live screen of the page (`StarScreen` on the `BrainController`, drawn by `scene/screenLayer.ts`, placed by `screen.ts`): it grows out of the star when the camera has stayed close for 0.3 s, faces the camera above the star, and folds back when the camera leaves; labels of nodes behind it are not drawn. Enter (or a click on it) opens the Forge window. While it is in view the brain window says so (`forge:screen`) and main sends frames (`forge:frame`, raw BGRA, at most 1024 px, every 250 ms at most): captures of the Forge window when it is open (once a second while it has the focus, so the pen's input never waits on main), else paints of a hidden offscreen copy of the page (same file, preload and session; muted, 4 fps, no navigation, closed a minute after the screen folds). Palette: *Concept Forge — fly to its star*, which makes the star when there is none.

## 9. AI chats (web + desktop)

`i` (or dropping a `.zip` / `.json`, or the palette) imports Claude's and ChatGPT's data exports (`packages/core/src/chats`): a small zip reader (stored, deflate via `DecompressionStream`, zip64; entries read on demand from the `File`), readers for Claude's `conversations.json` + `projects.json` / `projects/*.json` (the kept branch, text, artifacts, attachment text) and ChatGPT's message trees (`current_node` to the root; generated pictures and their prompts, canvases; hidden, system and tool messages dropped), and `planChatImport`: one note per chat under `<home>Resources/AI Chats/<Claude|ChatGPT>/` (else `<home>AI Chats/`), a hub + `Knowledge/` notes per Claude project (into `<project home>/AI Chats/` when an Aether project has its name), ChatGPT pictures into `Pictures/` next to their chat. Notes use standard frontmatter only; a `Source: <https://claude.ai/chat/…>` line is the note's identity on re-import (found anywhere in the vault), and only the `## Transcript` section of a chat that grew is rewritten. Chat text is written inert: `[[`, `#tag` and task checkboxes are backslash-escaped where the brain would read them (links and tags are read from the markdown source, so escapes hold), HTML block openers that would swallow the note are escaped, open fences are closed. The store writes it as one batch (create-only notes and pictures, `rewriteNote` for transcripts), after a confirmation. The AI link's `save_chat` writes the same format live. Guide: [AI-CHATS.md](AI-CHATS.md).

## 10. Chat in the brain (desktop)

`q` opens a chat docked over the brain (`ChatPanel.tsx`). The conversation lives in main (`chat-host.ts`: settings, the API key encrypted with `safeStorage`, conversations in memory) and runs in the MCP bundle (`src/mcp/chat.ts`), over the AI link's brain (`AiLinkHost.useBrain`, open with the vault while the chat is configured, link on or off). The model works through the AI link's own tools, called in-process (`BrainTools`: an MCP client over `InMemoryTransport`; the ChatGPT connector pair and `save_chat` left out). Claude: the streamed Messages API with a manual tool loop (`claude-opus-5-5` by default, `medium` effort, the `fallbacks: "default"` server-side fallback; Haiku 4.5 without either), `eager_input_streaming` tools; the system prompt (the companion guide + the Wellbeing playbook, cached, then a session block with About me and the check-in trends as the conversation started) and the tool list stay byte-identical for the whole conversation and the history only grows (preserved thinking, prompt caching); each user turn carries its local time. Ollama: `/api/chat` on a loopback address only, a shorter prompt and a smaller tool set; a model without tools answers without them. Events stream to the window on `chat:event`; the turn's `done` event comes last on that channel and finishes the answer.

The user's own notes live in `<home>Me/` (`src/mcp/me.ts`): `About me` (one section per area; `remember_about_me` appends dated bullets, never a task or heading), `Check-ins/Check-ins YYYY-MM` (one table row per check-in), `Wellbeing playbook` (from `companion.ts`, made once, the user's copy is the one read), `Chats/` (each conversation as an inert chat note tagged `brain-chat`; its transcript is rewritten in place as it grows). MCP tools: `about_me`, `remember_about_me`, `check_in`, `my_trends` (the last week against the weeks before; plain-fact notices), `wellbeing_playbook`. The companion never diagnoses, never advises medication changes, and gives the crisis lines when safety comes up.

## 11. The librarian (desktop)

`⇧ L` (`LibraryPanel.tsx`) copies every picture of a source folder or drive into a library folder, `<Type>/<Genre>/<Year>/`, and indexes it as notes. Main runs it (`library-host.ts`: settings, one job at a time, progress events on `library:event`, the model download, thumbnails of plan items through the thumbnail helper). `library/library.ts`: `analyze()` walks the source with an `FsVault` (the brain's skip rules, the library hidden), reads 64 KB headers (`meta.ts`: kind, size, EXIF dates, camera, software, generator marks), has the vision helper look at each new picture (cached by path, size and date in `library-looks.json`), places it (`plan.ts`, `classify.ts`: sure rules, then the model at 60 %, the nearest folder whose name says a type as whole words, the model at 40 %), marks duplicates (SHA-256 of same-size files, against the library too, and against pictures deleted from it: those stay out) and names (`gate (2).png`, a counter per name); `copyPlan()` copies each to a temp sibling while hashing it, sets its date, checks its size, links it into place (where the drive has no hard links: an exclusive empty placeholder, then the copy renamed over it; names either copy worker picked are reserved), appends it to `.aether-library.jsonl` (JSON lines, compacted after a run; the look cache is JSON lines too, read and written in chunks so the main thread never stalls), and writes the index notes (`MASTERIMAGES.md` as `type: project`, a folder note per type and genre, a note per taste; only the block between their `<!-- aether:library -->` markers is rewritten). The source is never written. The vision helper (`library/vision.ts`, `src/vision/`) is a hidden sandboxed window on its own scheme (`aether-vision://app/`, cross-origin isolated for ONNX threads) serving the built page, the ONNX runtime's WebAssembly and the model files; its session refuses every other request. It runs CLIP ViT-B/32 (Xenova's 8-bit ONNX export, transformers.js, WebAssembly) zero-shot: the picture's centre square at 224 px, normalized, against cached text embeddings of each set of descriptions, softmax of 100 × cosine. The model (`vision-model.ts`) is downloaded once on request from Hugging Face through a session of its own. Guide: [LIBRARIAN.md](LIBRARIAN.md).

### Find projects

`⇧ P` (`FindProjectsPanel.tsx`) turns the user's project folders into ★ stars in one go. Main (`projects.ts`, `vault:findProjects`, progress on `vault:findProgress`, `vault:findProjectsStop`) lists each folder of the last scan once, names only, and calls a folder a project for sure on an engine's project file, a git repository or a code manifest, or a guess on two or more art files; nothing is written by finding. The renderer (`find-projects.ts`) leaves out stars and archived folders and ticks the outermost finds; `store.makeProjects` writes the ticked ones' project notes, held per 100 (one graph rebuild each), with one toast.

## 12. The Unreal companion (desktop + `unreal/`)

A second renderer of the brain in Unreal Engine 5.8. The desktop app's **companion link** (`src/main/companion.ts`, `CompanionHost`) is an HTTP server on 127.0.0.1 (port 7459, off until switched on in the `a` panel or the palette), every request carrying a Bearer token compared in constant time, no CORS. While it runs, `companion.json` (address + token, mode 600) sits in the app's data folder for the viewer to find; it goes when the link stops (synchronously on quit). Routes: `GET /v1/hello`, `GET /v1/graph` (JSON from `renderer/companion-scene.ts`: per node id, title, kind, the brain's colour in the current colour mode, radius, parent index; links as index pairs; selection; layout; `limits` {nodes, ofNodes, links, ofLinks}; `ETag`, 304), `GET /v1/positions` (binary: `AEP1`, graph version, node count, ring count, then float32 xyz per node and 6 floats per orbit ring), `GET /v1/thumb?id=&size=` (a PNG, 64 to 1024 px on the longer side, of a picture node or of the cover of a folder, for ids of the published scene only, at most four at a time; the cover is what the brain window names in the scene's `cover` or, failing that, a pick from the scan), `POST /v1/select {id, open}` (relayed to the brain window: select and fly, or open). The brain window publishes only while a viewer asks (`companion:want`, dropped after 8 s without a request, asked again after 5 s without a publish, e.g. after a reload; while one reads, the window runs at full speed and its 3D view rests when it is not in front): the graph when it, the colours, the selection or the layout change (never the very same scene twice), positions up to 10 times a second when the layout moved. A big brain is cut to a budget first (`renderer/companion-bound.ts`: at most 12,000 nodes, 8,000 links and 400 orbit rings; suns, the Today hub and the selection always, then stars, folders and notes by importance, every kept node under the parent it orbits in the brain, positions from the brain window's own layout; `renderer/companion-feed.ts` decides what is published when: a new vault only once its layout has grown out into its places, the rings worked out from where the bodies finally sit, scene numbers that start from the clock so a reloaded window never repeats one). No note text leaves the app; nothing but select / open comes in. The viewer (`unreal/AetherBrainViewer`, a C++ plugin `AetherBrain`) reads `companion.json`, polls, eases toward the positions, and draws nodes, links and orbit rings as three instanced meshes with an unlit material reading colour and glow from per-instance custom data (made by `Content/Python/init_unreal.py` on the editor's first start, with an empty map), labels on suns, stars and planets, a fixed-exposure, bloom post-process, and the **space** (`AetherSpaceActor`, `B` cycles full / calm / off): nine parallax layers of generated star, nebula and galaxy sprites (a layer's centre lags the camera by `(1 - follow)` of its position, softly capped at a third of its radius), rocks in belts and zooming through, shooting stars and alien ships built from the engine's basic shapes, all pure functions of time (`Private/AetherSpaceMath.h`, plain C++ tested without Unreal by `unreal/tests`), lit by a warm key and a cool fill (materials `M_AetherSprite` and `M_AetherRock` made by the same script), and (v0.9.0) a **Niagara layer** (`AetherFxActor`, `N` toggles): five Niagara systems in `/Game/AetherFX` (`NS_AetherPulses`, `NS_AetherCorona`, `NS_AetherRipple`, `NS_AetherDust`, `NS_AetherShootingStars`, made once in the editor from `docs/UNREAL-NIAGARA.md`; a missing one is not played) played through pooled `UNiagaraComponent`s whose only input is their `User.*` parameters (Start / End as Position, Extent as Vector, Color, Duration, Size, Width, Radius, SpawnRate, Intensity), planned by `Private/AetherFxMath.h` (a numbered stream of events per effect, a link index built once per change of the graph, a fixed pool that drops rather than queues, nothing drawn before the brain's first positions); it flies with the mouse and WASD, picks by ray against node spheres, and posts select / open. After v0.10.1, **the Voyage** (`AetherVoyageActor`, `V`): an 8K nebula sky and 8K suns with a corona, three ships and four kinds of asteroid with PBR maps, all made in code when play starts (background threads, one job at a time, nothing stored in the project), an extra-large picture card on every folder that holds pictures (fetched from `/v1/thumb`, at most `MaxCards` held), and a flight of the player's interceptor to the selected folder along a curved route through asteroid fields that can be shot into pieces (cursor-aimed guns, shield and hull, an avoidance assist), ending in front of the folder's card where `Enter` opens it in the desktop app. Plain-C++ cores tested on the host (`AetherSkyMath.h`, `AetherMeshMath.h`, `AetherShipMath.h`, `AetherRockMath.h`, `AetherCombatMath.h`, `AetherVoyageState.h`). Procedural, not photographed; about 1.3 GB of video memory at the defaults (Sky Width, Sun Width, Map Size scale it down). Guide: [UNREAL.md](UNREAL.md), [UNREAL-NIAGARA.md](UNREAL-NIAGARA.md).

## 13. Reference boards (desktop + web)

A PureRef-style board of pictures, text notes and drawn marks, for keeping references next to the work. User guide: [REFERENCE-BOARD.md](REFERENCE-BOARD.md); keys: [KEYBOARD.md](KEYBOARD.md); the contract the pieces were written against: [design/reference-board.md](design/reference-board.md).

**A board is a markdown note** (`type: board` in its frontmatter), by default `<home>Boards/<Title>.md`, with its own pictures in `<home>Boards/<Title>/`. The board is the first `## Board` heading and the list under it down to its **last item line** (plus the lines that touch it), one readable line per item (a view line, pictures as `![[embeds]]` so the graph links the board to them, notes, pen strokes, lines, rectangles, ellipses). Everything else in the note, above the heading and after the board's last item line, is the user's and is kept byte for byte (a blank line after the last item starts it; the next heading does not end the board). A save rewrites every line of the span from the model: known attributes in a fixed order, a note always with `r=` and `fill=`, a rect or ellipse without a fill gaining `fill=`, groups counted again from 1. Lines the reader does not understand, and prose between the heading and the first item or between items, are kept but written right after the last item (without their blank lines); an attribute it does not know on a line it does is kept after the known ones when it is a plain name with a plain value, and dropped with a warning when it holds anything a markdown reader would take for a link, tag, emphasis or html (`packages/core/src/board/format.ts`: `parseBoard`, `serializeBoard`, `newBoardNote`, `isBoardNote`). What is written on the board (the text of notes and picture captions) is search text and counts as words, never as links or tags (`boardNoteParts`). Pictures are never edited: crop, flip, rotation, grey and opacity are numbers on the item, and export writes a new picture. Limits (`BOARD_LIMITS`): 1,500 items, 4,000 characters per note and 3,000 points per stroke that a user makes (a note already in the file keeps up to 100,000 characters and a stroke 50,000 points, and editing never shortens them), and a size budget of 500,000 characters for the board's items (`boardChars(doc)`, cached per item), enforced when the board **grows** (drawing, notes, pictures, paste: refused with *The board is full*; anything that keeps or shrinks the size is always allowed; reading a board over it warns). The floating window opens whole notes of up to 1,000,000 characters (`MAX_BOARD_TEXT`); pictures up to 150 megapixels and 64 MiB are shown (a picture over either that is in the vault is a *too large to show* placeholder, in the docked view and the window alike on the desktop; a dropped or pasted picture over 150 megapixels is refused before anything is copied; the web build, which cannot read a file over 64 MiB, says *can't be read* for those).

**Layers.** Core (`packages/core/src/board/`): the data model, the markdown format, pure operations on a `BoardDoc` (`ops.ts`, `arrange.ts`, `geometry.ts`, `palette.ts`), a 200-step `History`. UI (`packages/ui/src/board/`): `BoardController` (the whole interaction state machine, no DOM: tools, selection, drags, pen, pan, zoom, commands, history), `commands.ts` (`BOARD_COMMANDS`, the one table of commands, titles and keys that the palette, the cheatsheet, the board's menus and the key map are read from), `renderer.ts` (Canvas 2D: `drawBoard`, `exportBoard`), `imageCache.ts` + `imageLoader.ts` (pictures held as `ImageBitmap`s in tiers of 256, 1024 and 8192 px under a 128-megapixel budget, two decodes at a time, only for what is on screen), `BoardView.tsx` + `view/` (the React shell over a `BoardHost`: canvas, toolbar, style panel, menus, picker, note editor, drops and pastes, saving). The view knows nothing of the store or of Electron: everything it needs is a `BoardHost` (`api.ts`: `load`, `save`, `onExternalChange`, `pictures`, `toast`, `copyText`, `window?`).

**Saving.** The shell saves at the end of every gesture (a drag costs nothing until it ends, at most once a second while it runs; a gesture that ends within 250 ms of the previous final change rides the one-second throttle instead of being written at once, so a crash inside that second loses it), never for a pan or zoom alone (the view is kept in `localStorage` under the host's `stateKey` and rides along with the next real change), and again when the window blurs, hides or closes. A save is `serializeBoard(doc, rawLastRead)`: it merges into the text last read, so hand-written text survives, and it carries that text with it (`host.save(raw, expectedBase)`): a save when the note on disk is no longer that text is refused (`BoardChangedOutsideError`), never written over. When the note changes under an open board the session reads it again by itself: with nothing unsaved the outside board replaces the one on screen (the camera stays, the undo history starts again from it; an outside change that leaves the board part as it was changes nothing and keeps the history); with unsaved changes the board says so and its next save writes them over the **board part** of the note (what the outside edit did elsewhere in the note is kept); a refused save asks for that reload again each time it repeats. A board whose note is deleted or moved stays open (it holds the only copy of the latest work), says so, and its saves are refused until the note is back. A failed save keeps the board on screen, retries, and offers *Copy board text*; `store.addPicturesToBoard` and the pop-out stop when the open board could not be flushed (`ActiveBoard.flush(): Promise<boolean>`).

**Two hosts, one view.** The **docked host** (`board/dockedHost.ts`, `createDockedBoardHost(path)`) is the board over the store: `store.readBoard(path, { quiet? })` (the file as it is on disk, a pending editor draft saved first; `quiet` leaves out its own toasts for a reload of an open board), `store.saveBoard(path, text, expected)` (the per-note exclusive queue; refuses when the editor holds unsaved edits of the note or the file is not what was expected), `store.preview`, `store.readPicture` (`VaultAdapter.readAsset`, a whole picture, ≤ 64 MB; the desktop's `readAssetChecked` makes it reject with a `reason`: `missing`, `too-large`, `unreadable`), `store.importBoardPictures` (create-only into the board's folder, one answer per file, `<folder> pictures` when the vault leaves the first out), assets from `store.assets`. It tells the view of a change made elsewhere by watching the store's copy of the note against the last few texts it read or wrote (its own saves are not outside changes). The **floating host** (`apps/desktop/src/renderer/board-host.ts`) is the same board in a second window (`board.html`, one board at a time, `board:open`, `board:save(path, text, expectedBase?)` — which accepts only a vault `.md` that is already a board and ≤ 1,000,000 characters, and compares the note with `expectedBase` and writes in one step in main —, `board:read`, `board:assets`, `board:configure`, the close handshake `board:flush` / `board:flushed` (a close waits up to 1.5 s for the page to write), events `board:state` and `board:closed`; `src/main/board-window.ts`, `board-save.ts`). The window's page has a preload of its own (`board-preload.cts`: the board calls, the pictures and the clipboard, nothing else) and main answers it no other channel (`BOARD_PAGE_CHANNELS`), and on `board:read` / `board:save` only the path the window shows and on `vault:reveal` only a picture, a video or that board (`pageRefusal`), so it cannot reach other notes, not even other boards. A board is open in one place at a time: popping out saves, then opens the window; the app shows a card in the board's place when the board is open in it (*This board is open in its window · Bring it back*; from a card's ⧉ in the list the list stays as it was, and opening that board shows the card); the window closing hands the board back and the app loads the note again. Window settings (always on top, opacity on Windows and macOS, place and size) are `settings.board`.

**Joining the app.** Store: `View` has `'boards'`; `boardPath` (kept while the view is left), `lastBoardPath` (per vault), `boards()`, `openBoards()`, `openBoard(path)`, `closeBoard()`, `newBoard(title?, { open? })` (create-only note, title and file name unique, `Title 2`, `Title 3`), `addPicturesToBoard(paths, boardPath?)` (rewrites a board that is not open through `rewriteNote`: new pictures packed to the right of what is there, as many as fit the size budget with the rest counted and the budget named in the message; a board open in the view saves first, nothing is added when that save fails, and the view reloads by itself), `boardFolderOf(path)`, `showPicture(path)`, `showNode(id)` (select and fly, leaving any covering view: the palette's `⇧ Enter`). A save for a note the view never read (`expected` null) still only ever writes over a note that is a board. `importImages(files, folder, { quiet })` leaves out the selection and the "Added" toast for boards. The board last open is followed through a rename (in the store and in the key the `8` key reads after a restart). The camera a board remembers, and the copy of a board that could not be saved (offered as *Recover unsaved changes* when the board is opened again), are kept under `BoardHost.stateKey`: per vault location and path in the docked view; the floating host has none and keeps them per note path, apart from the docked view's. Keys: `8` and `⇧ B` (inside the view they go up: board → list → the board last open); the view consumes the keys it uses in the capture phase and the global handler ignores every other single key while it is up (a test presses every key and pins that none fires); `Esc` is the board's own ladder first, then closes the view. The palette has *Boards: open / show list / new board / open the selected note as a board / add the selected picture to the last board or a new one* and every board command as *Board: …* (offered while a board is open and enough is selected; the window rows are the desktop's). The picture inspector has *Add to board*. The active board registers itself (`board/active.ts`) so the palette and the pop-out code reach it without the React tree; the desktop app registers the window control (`setBoardWindowControl`, `renderer/board.ts`). Dropped files on an open board are the board's (the window's drop zone stands aside); dropped web addresses cannot be fetched (the app makes no network requests) and the board says so.

**Bounded.** The list is drawn a page of 24 cards at a time (ceiling 1,000, search for the rest) with each card's pictures loaded only while it is on screen (`PreviewUrls`: at most 4 fetches at a time, 120 idle previews kept, the rest revoked); a card's summary is parsed once per version of its note (200 kept); the picker lists the vault's pictures windowed; decoded pictures are held under the cache budget only; a view that is closed does no work.
