# Aether Brain — notes for agents and contributors

Aether Brain is a local-first **3D second brain**. Markdown files in a folder (or several folders / whole drives) are the only source of truth; the app renders them as a navigable neural map (notes = neurons, `[[wikilinks]]` = synapses, PARA folders = constellations, tags = colored fields, time = orbital rings). The default **system layout** is a cosmology (`docs/COSMOLOGY.md`, the contract the Unreal version is built to): each drive is a ◉ galaxy, every folder is a ★ star (a project's home folder the biggest), big pictures, videos, 3D models and long notes are ● planets drawn as extra-large thumbnails, small files are · moons, and how soon something needs you is its orbit's speed, and how much you use a folder is its star's brightness (`markdown/urgency.ts`). Claude and ChatGPT reach the brain through a local MCP server (the **AI link**, desktop only; see `docs/AI-LINK.md`). Since v0.4: the **Today hub** (`today:`) hangs above the sun with beams to every note holding one of today's tasks (the daily brief, derived, nothing written); **picture moons** (`image:<path>`) show each folder's newest images as thumbnails and `![[gate.png]]` links notes to pictures; the **Concept Forge link** (desktop, `g`) hosts the user's own `concept-forge.html` and files graded drawings (PNG + critique note) into a project's Critique planet (see `docs/FORGE-LINK.md`). Since v0.5: **AI chats** — `i` (or dropping the `.zip`) imports the Claude and ChatGPT data exports as one note per chat (plus Claude project hubs and knowledge notes, ChatGPT pictures), re-importable; the AI link's `save_chat` saves a conversation live (see `docs/AI-CHATS.md`). Since v0.6: **star galleries** — when the camera comes close to a project ★ star, every picture under its folder floats around it as a card on a turning sphere (`images.gallery` in the graph build, `galleryAnchors` / `placeGalleries` in `layout/system.ts`, the proximity check and card growth in `gallery.ts` + `BrainScene.tsx`, the open/fold policy in `BrainController`, `store.gallery` / `toggleGallery`, `⇧ G`); **videos** (mp4, m4v, mov, webm) are media like pictures — moons, cards, embeds — shown as one still frame with a ▶ badge, never played in the brain (`e` plays one in the OS player). Since v0.7: **games and weird folders stay out** (game libraries and folders holding an installed game or program are skipped, `installs.ts`; `⇧ H` leaves any folder out live, `FsVault.hidden`; the vault folders panel brings them back); **chat in the brain** (`q`: Claude with the user's key or local Ollama, over the AI link's own tools in-process; it knows the user through `Me/` notes — About me, check-ins, the Wellbeing playbook — see `docs/BRAIN-CHAT.md`); **the librarian** (`⇧ L`: copies every picture of a drive into a library sorted `Type/Genre/Year` with taste tags, an offline CLIP model in a hidden helper window, a manifest for reruns, and index notes that make the library a ★ star — see `docs/LIBRARIAN.md`). Since v0.8: **the Concept Forge star** — the project star that carries the Forge (`renderer/forge-star.ts`) shows a live screen of the page that grows out of it when the camera comes close (`StarScreen` / `ScreenHost` on the `BrainController`, `screen.ts` placement, `scene/screenLayer.ts` one quad + gold frame + beam, labels behind it hidden); main streams frames only while it is in view (`forge:screen` / `forge:frame`: captures of the Forge window when open, else a hidden offscreen copy of the page); `Enter` or a click opens the Forge window; **picture sizes** (v0.8.1) — `z` / the legend's M · L · XL: medium, large or extra large icons (`PictureSize`, `PICTURE_RADIUS` in `theme.ts`, through `nodeRadius(n, size)`; the system layout reserves a picture's drawn width; `settings.pictureSize` rebuilds the graph; 256 px thumbnail layers); **find projects** (v0.8.2) — `⇧ P` looks through the folders of the last scan for the user's projects (`src/main/projects.ts`: one listing per folder, names only; engine, git and code projects for sure, two or more art files as a guess) and `store.makeProjects` makes the ticked ones ★ stars (`renderer/find-projects.ts` picks what is offered and ticked, `components/FindProjectsPanel.tsx`; a vault on disk with at most one star gets a one-time toast); **the Projects board stays open on big vaults and a crash never blanks the window** (v0.8.3, v0.8.4) — one link index per board instead of one per task row; the board draws only what is in view (cards windowed, tasks and folder chips paged, long texts cut) and nothing while closed; `ErrorBoundary` around each part of the app (`components/ErrorBoundary.tsx`) and a reload of a dead page with a message (`src/main/crash.ts`); **the Unreal companion** — `unreal/AetherBrainViewer`, an Unreal Engine 5.8 project (C++ plugin `AetherBrain`, built by the user, not by CI) that draws the brain live from the desktop app's companion link (`src/main/companion.ts`; the brain window publishes the scene through `renderer/companion.ts` + `companion-scene.ts`; see `docs/UNREAL.md`), and (v0.8.2) a living **space** around it (`AetherSpaceActor`, `B` cycles full / calm / off): nine parallax layers of generated star, nebula and galaxy sprites, asteroid belts and rocks zooming through, shooting stars, alien ships (saucers, dart squadrons, mother ships, orb scouts) built from the engine's basic shapes, every mover a pure function of time (`Private/AetherSpaceMath.h`), lit by a warm key and a cool fill (`M_AetherRock`, `M_AetherSprite` made by `init_unreal.py`). Since v0.9: a **Niagara layer** in the Unreal viewer (`AetherFxActor`, `N` toggles; pulses of light along links, a breathing corona per sun and a halo on the selection, a ripple on selection, dust round the camera, shooting stars): five Niagara systems in `/Game/AetherFX` that are made by hand in the editor from `docs/UNREAL-NIAGARA.md` (a `.uasset` can't be written outside the editor, so none are in the repo and a missing one is simply not played), played through pooled components by their `User.*` parameters only (the table in the doc is the contract, a test pins it), planned in `Private/AetherFxMath.h`. Since v0.11: **suns that open** (a closed sun shows only itself; a click opens its planets, the bar at the bottom of the view picks Closed / Planets / Planets + moons, `s` and `⇧ S` step them; `docs/COSMOLOGY.md`, *Suns open*), **a real sky** behind the brain (a procedural Milky Way, nebulae, distant galaxies and real stars, baked once into a cube map: `scene/sky*.ts`), **organised orbit rings and labels** (`scene/labelPlace.ts`), **sound** (a synthesised note for every click, a run when a sun opens, `⇧ M`: `ui/src/audio/sounds.ts`) and the **dormant Bio star** (the blue star stands where the `Bio` folder will be before it exists, and one button makes it).

## Non-negotiables

- **Local-first.** No accounts, no telemetry, no analytics SDKs, no outbound requests from the renderer. Electron's main process blocks http(s) in production. The AI link's HTTP server binds `127.0.0.1` only and every request carries a secret token. The Concept Forge window is the one exception by design: it is the user's own page in its own session (`persist:forge`), so its Deep Critique can reach the vision AI the user configured there; the brain window's session still blocks everything, and the Forge page reaches the brain only through `window.aetherForge` (projects + save, validated in main). The Forge session serves no file but the chosen page (its own `file:` handler plus a CSP header on the page, since workers bypass protocol handlers): the page can't read the vault.
- **The brain's chat is opt-in network use.** With Claude chosen and the user's own API key set (`q`, ⚙), main sends the conversation and what the chat's tools read to api.anthropic.com (the SDK runs in main, from the MCP bundle; the renderer still makes no requests and never sees the key, kept encrypted with `safeStorage`). Ollama is reached only on a loopback address. Nothing is sent before the user sets a key or a local model and writes. The companion never diagnoses or advises medication changes, and when safety comes up stays with the user and turns to their own people: no hotline lists, no phone numbers unless they ask (`src/mcp/companion.ts`). Nothing reads the Bio star's pages (sleep, food, meds, exercise, drugs, mental health) on the user's behalf: the chat opens one only when a question needs it, what it reads goes to Anthropic only with Claude chosen, and a folder left out with `⇧ H` is out of its reach (`docs/BRAIN-CHAT.md`, *Your Bio notes*). The day-planning nudges (`renderer/nudges.ts`, `components/NudgeCard.tsx`, the `nudges` chat setting in main) are quiet by contract: no sound, no number and nothing about what is late in a card's text, at most three a day, only when the chat is set up and something is on today's brief. Their windows and wording are pinned to `docs/BRAIN-CHAT.md` and to the coach's guide by `nudges.test.ts`.
- **The tunnel is opt-in network use, and never outlives what asked for it.** The AI link panel's Start tunnel (`main/tunnel.ts`, `TunnelHost`) runs cloudflared's quick tunnel to the link's port on `127.0.0.1` for ChatGPT and claude.ai. cloudflared comes from the PATH, else it is downloaded once, on a press that first said what, from where and how big, through an in-memory session of its own (`aether-tunnel-download`), from ONE pinned release (`CLOUDFLARED_VERSION`, Windows x64 only: elsewhere the user installs it) and kept only when its size and SHA-256 are the pinned ones; the app's own copy is hashed again before every start. The tunnel is off whenever the app starts, is told to end synchronously on quit (`before-quit`, before the link stops), stops when the link goes off or changes port (`aiConfigure`), and a pid file lets the next start stop one a killed app left behind (only a process named cloudflared is ever stopped). A toast says when it opens and when it ends by itself. A newer cloudflared means new numbers in `tunnel.ts` (GitHub shows each file's SHA-256), pinned by `tunnel.test.ts`.
- **The companion link is off by default, loopback only, token-guarded, and reads like a viewer.** `CompanionHost` binds 127.0.0.1, needs `Authorization: Bearer <token>` on every request, sends no CORS headers, serves only what the brain window publishes (titles, kinds, colours, radii, positions, links — never note text) and takes only select / open of a node in the current scene. The brain window publishes only while a viewer asks. `companion.json` (address + token, mode 600) exists only while the link runs.
- **The star screen's frames are pixels, not files.** Main sends the Concept Forge page's own paints and captures (`frameOf`: resized, raw BGRA, ≤ 1024 px) to the brain window only, and only while the screen is in view; the hidden copy of the page is offscreen, muted, takes no input, never navigates, and closes a minute after the screen folds.
- **The main process never decodes pictures.** Thumbnails are made in the hidden helper window (`thumbnailer.ts`); `nativeImage` decoding runs on Windows' UI thread and freezes the app. Videos neither: main checks a video's first bytes (`videoKindOf`, VIDEO_HEAD_BYTES) and serves the file to the helper on a one-job `aether-video://clip/<token>` address (byte ranges, its session only, 404 once the job ends, open streams ended with it); the helper takes one still frame and never plays it. The helper encodes with `toDataURL`, not `convertToBlob` (a hidden page stops getting the idle time it waits for). A 3D model (`.glb`) is read whole here (at most 64 MB), checked by its first bytes (`modelKindOf`) and sent as bytes: the helper's preload draws it with a small software rasterizer (`rasterGlb`; the helper has no GPU; bounded vertices, triangles and time; nothing a file names outside itself is ever read), and main never parses one. The look of a model is `modelBrightness` and `MODEL_EXPOSURE` in `thumb-preload.cts`.
- **The librarian copies, never moves, and its eyes are offline.** `copyPlan` never writes, renames or deletes anything in the source; each picture goes to a temp sibling (`.aether-tmp`, skipped by scans) and is linked into place without replacing anything (where the drive has no hard links: an exclusive empty placeholder, then the copy renamed over it); a taken name gets ` (2)`. Index notes: only the block between the `<!-- aether:library -->` markers is the librarian's. The vision helper's session refuses every request but its own `aether-vision://app/` scheme (page, ONNX runtime, model files from disk); the only network use is the model download, once, when the user presses Download (its own in-memory session). Main reads picture bytes and sends them; it never decodes them.
- **Markdown is the format.** Never invent a proprietary note format. Frontmatter keys: `title, tags, created, updated, status, area, type, aliases`. Wikilinks: `[[Title]]`, `[[Title|alias]]`, `[[Title#Heading]]`, `![[Title]]`.
- **TypeScript strict** everywhere, `noUncheckedIndexedAccess` on. Run `pnpm typecheck` before committing.
- **Main thread stays free.** Graph physics runs in `packages/graph/src/layout/layout.worker.ts` (d3-force-3d; the system layout is the analytic `layout/system.ts`, also in the worker). Never run the simulation on the main thread.
- **One draw call per thing.** Nodes = one `InstancedMesh` (+ one for halos); edges = one `LineSegments`. No per-node meshes, no per-node React components.
- **Every feature has a keyboard path.** If you add a UI action, add a key in `packages/ui/src/hooks/useKeyboard.ts` and a command in `packages/ui/src/commands.ts`, and document it in `docs/KEYBOARD.md` (and the cheatsheet in `components/Help.tsx`). Desktop-only UI uses the extension points instead (below).
- **Writes on behalf of an AI** go through `FsVault` and only ever write `.md` notes, plus one kind of picture: `save_image` (`mcp/pictures.ts`, `Brain.savePicture`) writes create-only, through `FsVault.createBinary` after `assetBytes` (the bytes must really be a PNG, JPEG, GIF, WebP, BMP or AVIF, at most 40 MB; the next name is taken rather than replacing anything). Its three sources have separate rules, each pinned by `mcp-pictures.test.ts`: `data` (base64, at most `MAX_PICTURE_DATA_CHARS`, a 40 MB picture, inside the HTTP link's 64 MiB request cap `MAX_BODY_BYTES`: a model types only small ones, the plugin's bridge reads a file and sends it whole), `path` (a file on this computer: only when the server runs there, `McpServerOptions.localFiles`, which only stdio sets; never the HTTP link a tunnel reaches nor the in-app chat; a network or device path is refused and a symlink is judged where it points) and `file` (ChatGPT's `openai/fileParams` object: downloaded only from ChatGPT's own file hosts, `OPENAI_FILE_HOSTS` plus `AETHER_FILE_HOSTS`, over https on the standard port with no credentials, redirects judged one by one, size and time capped; a model can write any address into an argument, and a fetch of one it chose could carry notes out in the query string). It is the only tool marked `openWorldHint`. No MCP tool deletes a note.
- **The app lends the AI link its pictures and its window, nothing more; the plugin's bridge is a pass-through with one door.** `find_pictures`, `get_image` and `show_in_brain` (`HOST_TOOLS`) are registered only when the server was given `McpServerOptions.pictures` / `.show`, which only the running app does (`main/ai-pictures.ts` over the last scan and the thumbnail helper, so a picture is still decoded in the helper and never in main; `show` is one `ai:show` message to the brain window, whose `showForAi` leaves the camera alone while a note is dirty). The standalone server, the `.mcpb` manifest (`pack-mcpb.mjs` leaves `HOST_TOOLS` out) and the in-app chat have none of them. They are reads: they stay on in read-only mode and write nothing, and `get_image` answers text first, then the image block, so a connector that drops images still has the answer. `plugin/aether-brain/bin/bridge.mjs` (zero dependencies, `127.0.0.1` only, the port and key read from the app's own `settings.json` on every message, `AETHER_SETTINGS` to point it at another copy) forwards every message as it is and rewrites exactly one: `save_image` with a `path`, whose file it reads itself with the stdio server's checks (written again in plain JS, pinned against the app's own `imageKindOf` and `isImageName` by `plugin-bridge.test.ts`) and sends as `data`. With the app unreachable it answers on its own (instructions, the one tool `aether_brain_status`) and sends `tools/list_changed` when that changes. The HTTP link itself still never takes a `path` from its callers. The plugin's version (`plugin.json` and its entry in the root `.claude-plugin/marketplace.json`) is bumped with the app's.
- **Pictures are written create-only and checked.** The renderer writes an image only through `createAsset` (image extension, ≤ 40 MB, file signature must match a real image, never over anything, EEXIST → the next ` 2` name); `openAsset` opens existing vault pictures and videos only (a video must start like one; `shell.openPath` would run anything else). Videos are shown (`isMediaPath`), never written (`isImagePath`). Models are shown (`isAssetPath`: pictures, videos and `.glb`), never written and never on a board: `isMediaPath` is the boards' list and stays pictures and videos, and a model is opened through `FsVault.modelAbs`, a door of its own, so `assetAbs` (picture reads, the board window) never returns one; the board window is also refused a model's thumbnail and `openAsset` (`pageRefusal`).
- **Prefer fewer dependencies.** If a library fights the product, write the piece (see `frontmatter.ts`, `wikilink.ts`, the label overlay, the zip reader in `chats/zip.ts`).
- **Imported chat text is inert.** What a chat says must never become a link, tag or task of the brain. Each message is kept whole behind `> ` (`quoteMarkdown`: a quote closes whatever it holds, and the line-by-line task scan never reads a quoted line); `inertMarkdown` escapes what the parsers would still read (`\[\[x\]\]` on both sides, `\#`, a GFM task's `\[ ]`), parses again and fails closed (`blanketInert`); the parsers skip characters a text node's source wrote escaped (`charOrigins`). Only the note's own lines (header, hub lists, a `save_chat` summary) are live.

## Data flow

`VaultAdapter.list()` + `listFolders()` + `listAssets()` → `parseNote` (per file) → `buildGraph` (resolves links vault-wide, creates ghost nodes for unresolved targets; in the system layout also folder nodes and structural parents) → `SearchIndex.rebuild` → store → `BrainController.setGraph` → `LayoutEngine` posts to the worker → positions `Float32Array` (+ orbit rings) → `BrainScene` writes instance matrices each frame.

The store passes `loadVault` / `applyChanges` its folder set, its picture set (`assets`, copy-on-write like the folders) and a graph-options callback that asks for folder nodes only in the `'system'` layout (root title, mount labels, depth, expanded folders), picture moons there (`images.moons`; linked pictures in every layout), and the Today hub (`today: { brief }`, with the brief computed once per rebuild by `dailyBrief`). Crossing system ↔ other layouts, changing depth or expanding a folder rebuilds the graph and calls `controller.setLayoutMode(mode, graph)`.

Edits go through the store (`saveDraft`, `writeNote`, `moveToArea`, `updateProject`, `editTask`, `createFolder`, …) → adapter write → `applyChanges` (incremental parse + full graph rebuild, ~1 ms / 100 notes) → controller keeps previous positions so the layout doesn't jump. External changes (other apps, the AI link) arrive through `adapter.watch` and take the same path, folders included (`addDir` / `unlinkDir`).

Multi-root vaults (e.g. `D:\` + `F:\`): every vault path starts with the root's mount (`D/Projects/x.md`); single-root paths are unchanged. New notes go under `store.homePrefix()` (the first mount); `moveToArea` keeps a note on its own drive.

## Conventions

- Store actions are the API; components don't touch adapters directly.
- Nothing a view draws is unbounded: a list that can hold thousands of rows (project cards, tasks, folder chips, search hits, Find projects rows) is windowed (`windowing.ts`, fixed-height rows) or drawn a page at a time with a *Show more*, and long texts are cut (`truncate`). A drawn element costs a DOM node and a React fiber (3 to 5 KB): 100,000 task rows were ~10 GB and killed the window, while the JS heap stayed small, so only drawing less helps. **Text costs by its length, not only by its elements:** an imported chat of 1 MB took ~1 GB to open in the editor, one of 16 MB ~10 GB (the text box is ~0.5 GB per MB: Chromium makes two nodes per line of a `<textarea>` and lays every line out; the preview ~0.25 GB per MB), so `MarkdownPreview` draws a prefix of a note (`preview.ts`: 60,000 characters, *Show more* to 300,000, embeds 20,000) and a note over 400,000 characters opens read-only with no text box. Never put an unbounded string into a text box, a `<pre>` or a markdown render. A view that is closed does no work: `ProjectsView` is a wrapper over `ProjectsBoard` for that reason (its memos used to run on every note change while hidden).
- **A note is read as markdown only up to `PARSE_MAX_CHARS` (120,000 characters).** micromark costs about 1.2 s and 300 MB per MB it reads, one huge list or quote takes quadratic time (2 MB of one list: 74 s; 4 MB of a chat: 3.5 minutes), and a note of ~12 MB runs the renderer past its hard 4 GB (Electron 44: the heap cap is fixed, `--max-old-space-size` does nothing) *while the vault is loading*: the user saw one star, everything clumped, then "ran out of memory". `parseNote` reads the first 120,000 characters (cut at a blank line), sets `ParsedNote.partial`, keeps the rest as search text up to `PLAIN_MAX_CHARS` (250,000), counts its words without building a list, and reads no links, tags or headings past the cut; an imported chat (tag `ai-chat` / `ai-project`: its text is inert) is read only up to `PARSE_MAX_CHARS_CHAT` (40,000); `loadVault` yields to the event loop every 40 ms, indexes the search text in slices (`SearchIndex.rebuildAsync`, swapped in at the end) and main sends the notes a page at a time (`pages.ts`, 12 MB a page): ONE reply with the text of every note was larger than a message may be for a vault of 300 MB of chats, and the whole app died ("Trace/breakpoint trap"); a note file over 64 MB is not loaded at all (it stays on disk, untouched). Every new per-note pass over the whole text needs the same bound. Main looks at the brain page's memory every 2 s (`MemoryTrail`, `crash.ts`) and a dead page leaves `crash-reports/crash-<time>.json` in the user data folder and says in its dialog how much the page was using.
- **A crash while a vault is opening never loops.** The window reloads itself after a crash and the app reopens the remembered folders at launch: with folders too big for the page (whole drives), that was open, die, reload, open, die, a box saying *ran out of memory* again and again and no way to pick other folders. `StartupGuard` (`main/startup-guard.ts`) writes `startup.json` when `openVault` begins and removes it when the page has had the vault loaded for `SETTLE_MS` (60 s, `renderer/startup.ts`; the page says `startupSettled`, from the brain window only) or when the app quits by itself without the page having died. A page that finds the note (`startupInterrupted`, asked in `boot()` before `lastVault`) does NOT reopen the folders: the welcome screen says what happened (the report's memory sentence and the vault's counts, `interruptedMessage`) and offers *the same folders without pictures and videos* (`openVault(roots, { pictures: false })`: `maxAssets: 0`, for the session), *the same folders again*, or other folders. Crash reports carry the vault's counts (`vaultCounts`). The layout worker's failures are told too (`LayoutEngine.onError` → `BrainEvents.onLayoutError` → a toast): a worker that threw used to leave every body at the origin, one clumped star and no orbits, with no word.
- Nothing per row may build anything per note. A `LinkResolver` (or any index of the vault) belongs to a whole view and is built once per `notes` / `revision`, lazily when it is needed; a row that makes its own (the Projects board's task rows did) costs notes × rows in time and memory, and in a big vault that is a frozen or crashed window. A part of the app that can throw while drawing sits in an `ErrorBoundary` (`App.tsx` wraps every overlay; desktop panels in `renderer/main.tsx`): without one, React unmounts the whole window and the user sees nothing.
- A project is decided **only** by `isProjectNote(note)` from `@aether/core`; `meta.type` is `'project'` for every note under a Projects folder at any depth. `setProjectFields` throws on frontmatter it can't parse — callers catch and show the error (the store toasts). `updateFrontmatter` / `rewriteFrontmatter` patch changed keys in place (comments, untouched values, BOM and line endings survive) and leave a block they cannot parse alone. New notes are always created with `adapter.create` (fails with EEXIST, never overwrites); store rewrites of one note run one at a time and start from the file on disk.
- Store rewrites of one note (tasks, project fields, `moveToArea`, `patchFrontmatter`, renames) first save a dirty editor draft of that note and stop (toast) when it can't be saved, so a draft is never overwritten. Task `line` numbers count in the saved note (what the board shows); the store follows them into the just-saved draft.
- Windows and macOS file names are case-insensitive: new notes and folders reuse the vault's existing spelling of a folder (`D/inbox`, not a second `D/Inbox`), and creating never replaces a note whose id differs only in case.
- Notes the chat importer (and `save_chat`) wrote are known by the `Source: <https://claude.ai/chat/…>` (or `chatgpt.com/c/…`, `claude.ai/project/…`; `chatUrlOf` spells an address one way) line in their header — above the first `## ` heading, so a line quoted in a transcript never counts — wherever they were moved. Only a note tagged `ai-chat` (`ai-project` for hubs) is ever rewritten: a chat's transcript from `## Transcript` to the `*— end of transcript —*` line, only when it has grown (`save_chat` also replaces its `## Summary`); a hub's `## Project` section to its end. Chat and hub titles are unique vault-wide (links resolve by title, file name and alias).
- The parser guards itself: `tameNesting` and `tameDelimiters` (same-length rewrites inside `parseMarkdown`) keep micromark away from its quadratic paths (thousands of nested containers, thousands of `*`/`_` in one paragraph); chat text also goes through `tameChatMarkdown` before it is written.
- **A force layout's inputs are always finite.** d3-octree's `cover` ignores a NaN coordinate but loops forever, allocating a node a pass (about a gigabyte a second), on an infinite one, and the layout worker shares the window's process: one `Infinity` in constellation or orbit made the window *run out of memory* at the first tick, every body at the origin (one clumped star, no orbits, nothing answering). It got in through a link strength of `0.9 / min(degree, degree, 12)`: a Today beam goes from the hub to a note with a task due today, the beam is not in the note's degree, and a note with no links has degree 0 (a whole-drive vault is mostly such notes). `layout/safe.ts`: `linkStrength` never divides by less than 1, `finiteOr` for places carried over from an earlier layout, `healBodies` puts back any body that is not finite before every tick, and `enterSystem` takes a start place that is not a number for unknown. A new force, strength or anything a force reads needs the same care, and a test through the real worker (`worker.test.ts`, *force layouts stay finite*: on the old code that test kills the process, exit 134, in about a second).
- **The cosmology is a contract** (`docs/COSMOLOGY.md`): drive = galaxy (so is a project folder whose note says `scale: galaxy`: `planGalaxies` in `graph/galaxies.ts` settles which marks count, three levels counting the vault or a drive as the first and 64 marks, shallowest first; `build.ts` lifts it onto the galaxy above it as `GraphNode.parent` and sets `FolderNodeInfo.galaxyLevel`; `isGalaxyNode` is the one predicate the legend, tiers, owners and the viewer's `body` follow; layout role code 4; every galaxy has a faint spiral plate under it, `scene/galaxyDisc.ts`: ONE instanced mesh, fitted to the galaxy's outermost orbit ring, additive and far under the bloom threshold; the viewer's `kind` NEVER changes, only `body: 'galaxy'`, and a `galaxy` body hangs only from a galaxy, the origin or nothing), folder = star (its size grows with what it holds, `FolderNodeInfo.weight` through `nodeRadius`, minus what a galaxy took with it; the order of ceilings is drive 16 > galaxy you marked 15 > Bio 11 > project star 9.2 > board sun 9 > plain star 8), big visual file or long note = planet (`isPlanetNode`: a picture, video or model of 48 KB or more, or one nobody has sized; a note of 3,000 words or more), small file = moon; **a reference board with pictures on it is a sun** (`assignBoardSuns` in `graph/build.ts`: the pictures on it take it as their orbit parent instead of their folder, the first board by id when several hold one, `GraphNode.board` marks it; drawn big and mint-white, `BOARD_SUN_COLOR`, `nodeRadius`, always labelled `▣`; flying to it frames its system; sent to a viewer as a `star`; the other layouts are unchanged). Urgency comes from open tasks only (`markdown/urgency.ts`, a note's most urgent task; a picture's embedding note; a folder's whole system, saturating) and is **orbit speed** (rings never mix heat bands, so a ring has one speed: `urgencySpeed`; calm mode, `⇧ O`, holds it to a normal orbit's pace with `calmSpeed` and a second clock in the layout worker, never by changing the layout, so toggling it or rebuilding moves nothing). **Star brightness is NOT urgency: it is how much you USE a star** (`vault/activity.ts`: opening a note counts 1, saving it 2, the same kind with the same note within 20 s once, a score halving every 14 days; a folder is as bright as its whole system, `computeActivity`; kept in the window's localStorage per vault (`aether:activity:<location>`), NEVER in the vault and never sent anywhere beyond the viewer's scene, at most 4,000 notes, `forgetActivity` and the palette's *Forget which folders I use* clear it; the controller holds the numbers, `BrainController.activity`, and only recolours). A viewer is sent the original `kind` names unchanged (`companionKind`: sun, star, planet, moon, picture), the cosmology in `body`, `urgency` and `activity` (`companionBody`; `activity` is optional, to the hundredth, a star's brightness), and the scene cut ranks by structural classes of its own (`companion-bound.ts`: root or drive, project, folder, note): change one and check the others. `cleanGraph` in main whitelists the fields a node may carry, so a new field must be added there too (or it is dropped on the way to the viewer). A viewer never lays the sky out itself: positions come from the brain window's layout. **The Bio star** is the one blue star: the folder `Bio` at the vault's home (`BIO_FOLDER`, `vault/bio.ts`; `FolderGraphOptions.bio` is its path as the vault spells it, `FolderNodeInfo.bio` marks the node), drawn bigger than any other star (radius 9.5 to 11), `BIO_STAR_COLOR` blue (a deep body colour: the scene shows colour × glow with no tone mapping, so the lighter blue first tried clipped to cyan at that glow), a `BIO_STAR_HALO` aura wider than any other body's, always named `✚ Bio` in `BIO_STAR_LABEL_COLOR`, burning at `BIO_STAR_GLOW` whatever the urgency; the build marks a folder that exists and pins it and invents one only when the store asks for the dormant star (`FolderGraphOptions.bioPlaceholder`: a childless star with `folder.placeholder`, the real folder's own id so making the folder turns it into the real star in place, not a sun (`isSunNode`), never in a read-only vault), a drive is never it, and the viewer is sent it as a `star` that the scene cut always keeps. `store.makeBio` (the palette's *Create my Bio star*, the *Make it* toast of `⇧ I`, the inspector's button) writes the missing pages of `planBio` create-only (never numbered, never over a page that is there under any letter case); the six pages (sleep schedule, food, meds, exercise, drugs, mental health) are headings and empty lists with no advice, no number, no task, link or tag, and `bio.test.ts` reads them for it.
- **Suns open into planets, then moons.** Which bodies show is a view of the brain window, never part of the layout, the graph or what a viewer is sent. `packages/core/src/vault/cosmos.ts` has the pure parts (`SunLevel`, `isSunNode`, `bodyTiers`: 0 always shown, 1 from planets, 2 from moons; `bodyOwners`: the sun each body belongs to; `bodyOrder`: every sun before what it owns; `sunCounts` for the bar). `BrainController` holds the levels (`setSunLevel`, `setSunLevels`, `sunVersion`); the store keeps them per vault in localStorage (`aether:suns:<location>`, `chooseSun`, `cycleSun`, `toggleAllSuns`, `pickBody`, and `openSunsFor`, which every path that sets the selection runs so a hidden body is never selected while hidden). In `BrainScene.tsx` the frame loop turns levels into targets (`scene/reveal.ts`, one pass in `bodyOrder`, no allocation), eases each body's reveal and draws bodies at `drawPos` (pulled toward their sun by how little is revealed); picking and labels ignore bodies that are barely out. The folders directly under a galaxy are always shown; there is no "urgent bodies never hide" rule (it kept every urgent note beside a closed star on screen).
- **The sky and the sound are pure data plus one GPU bake and one synth.** `scene/skyData.ts` (constants and the stars, a function of a seed), `scene/skyShader.ts` (GLSL strings), `scene/sky.ts` (`bakeSky` into a 1024 cube render target, the far-plane dome, the star points; a failed bake falls back to haze); nothing in it is a file and it stays under the bloom threshold. `ui/src/audio/sounds.ts` is Web Audio synthesis only (`soundPlan`, `sunRun` pure; at most 14 notes at once; silent with no AudioContext); the nudge cards stay silent.
- Star galleries never move anything: a card that is also a moon or a linked picture keeps its node and its orbit slot (its parent's extent and rings are unchanged); a card in the graph only for the gallery (`gallery.only`) is parented to the star but left out of every extent and ring. Cards are placed relative to their star (`SystemLayout.anchor`, always a strict ancestor), and drawn at the size the layout gives them (`engine.cards`, sent with the rings). The camera opens a gallery (`controller.nearStar` from the scene, every 150 ms, measured where the camera's flight ends and at the point it looks at; it opens after a 0.3 s dwell, never during the first framing flight) and the store owns what is drawn (`store.gallery`, transient); a fold shrinks the cards first, then `onGallery(null)`.
- Node ids that are not notes: `folder:<vault path>` (`folderKey`, `isFolderId`, `folderPathOf`), `ghost:<target>`, `image:<vault path with extension>` (`imageKey`, `isImageId`, `imagePathOf`) and the Today hub `today:` (`TODAY_ID`). Anything that takes a note id guards with `isVirtualId`. Picture link targets (`![[gate.png]]`) never become ghosts.
- No `window.prompt` (Electron doesn't implement it): a command that needs text opens an in-app form (`store.requestForm`). `window.confirm` works.
- Desktop-only UI plugs into `@aether/ui` through extension points instead of editing the package: `registerCommands` (palette), `registerKey` (single key, same guards as the built-ins, built-ins win, returns an unregister function) and `registerHelpRows` (cheatsheet).
- Main-process writers (IPC handlers, the AI link) call `watcher.noteSelfWrite(path, content)` (content `null` for deletions; renames: `noteSelfWrite(from, null)` + `noteSelfWrite(to, content)`) so their own edits aren't echoed back. `FsVault.read/stat` return null for ignored or unresolvable paths; `write/mkdir/rename/remove` throw.
- The Unreal space's logic lives in `unreal/.../Private/AetherSpaceMath.h`: plain C++ with **no Unreal types**, so `unreal/tests/run.sh` can compile and test it anywhere; `AetherSpaceActor.cpp` only turns its answers into transforms. Anything new the actor asks of Unreal's API must also be added to `unreal/tests/ue_stubs/UEStubs.h` (the stand-in is written from memory of Unreal 5's API: it catches our own mistakes, not API drift). Everything that moves is a pure function of time; keep it that way.
- The Niagara layer follows the same rule: `Private/AetherFxMath.h` (no Unreal types, tested by `fx_core_test.cpp`) plans every effect, `AetherFxActor.cpp` only turns plans into `User.*` parameters (the fake Niagara components in `ue_stubs/NiagaraComponent.h` record every call; `fx_actor_harness.cpp` pins the parameter names, types and the no-reuse-while-busy rule). Its budgets are fixed (a pool per system, a link index capped at 200,000, at most six starts a frame, late events dropped): nothing it plays is unbounded. Every helper in an actor's anonymous namespace carries an `Fx` / `Sp` prefix (or lives in a shared header): Unreal's unity build joins a module's .cpp files, so two files defining the same helper compile alone and break together (`tests/unity_check.cpp`, the fifth `run.sh` stage, joins the two actors). A new User parameter or system must be added to `docs/UNREAL-NIAGARA.md`'s contract table too (`apps/desktop/test/unreal-space.test.ts` checks it), and the plugin's `VersionName` in `AetherBrain.uplugin` moves with the app's version (the same file checks it).
- Nothing sent to a viewer is unbounded either: `companion-bound.ts` cuts the scene to `COMPANION_BUDGET` (the budgets are targets, a kept node brings the chain of folders above it), and the viewer has its own backstops (`AetherScene.cpp`: 12 MB of graph read at all, 50,000 nodes, 100,000 link numbers, 2,000 rings) so that a scene from an older or other build is refused or truncated, not drawn into a stall. Positions come from the brain window's own layout, never from a seed: `LayoutEngine.placed` / `answered` / `carried` say whether they are places, `CompanionFeed` holds a new vault's first frames until the ease is over and judges the rings only by the settled places. A change to what is published needs a test against the real layout engine and worker (`companion-feed.test.ts`); a change to `AetherBrainActor.cpp` or `AetherScene.cpp` needs a check in `brain_actor_harness.cpp`, and anything new they ask of Unreal's API must be added to `unreal/tests/brain_stubs/FakeUE.h` with the engine's own signature.
- **Reference boards.** A board is a markdown note (`type: board`); the board is its first `## Board` heading and the lines down to its **last item line** (plus lines touching it), and everything else (the text above, and the text after the last item line, even another heading) is the user's and survives a save byte for byte (`serializeBoard(doc, raw)` merges into the text last read). The span itself is rewritten from the model on every save: every item line in canonical form, lines the reader does not understand and prose between the heading and the items kept but written right after the last item, unknown attributes kept after the known ones when they are plain names and values (anything a markdown reader would read is dropped, with a warning). Pictures are never edited: crop, flip, rotation, grey and opacity are numbers on the item and an export writes a new picture. The view saves at the end of each gesture (a drag only once it ends, at most once a second while it runs; a gesture within 250 ms of the previous final change rides that second), never for a pan or zoom alone; a save carries the text it was made from (`save(raw, expectedBase)`) and is refused when the note on disk is not that text (`BoardChangedOutsideError` in the docked host; the floating host sends the base with the write and main compares in the same call, and the saves of one note take their place in line in the order they were asked, before anything is awaited: judging a save takes file calls of uneven length and a busy machine used to let a later save overtake an earlier one), never written over: the session then reads the note again, and its unsaved changes win over the board part (with a message); an outside change that replaces the board on screen starts the undo history again from it. A board whose note is deleted is kept open, not closed. The board's items have a size budget (`BOARD_LIMITS.noteTotal`, core's `boardChars`) that is enforced when the board GROWS, never when it shrinks; the floating window opens whole notes up to `MAX_BOARD_TEXT` (1,000,000 characters). Decoded pictures are held only under the cache budget (`ImageCache`: 128 megapixels, three tiers, two decodes at a time) and only for what is on screen; a picture over 150 megapixels or 64 MiB is a "too large to show" placeholder in both hosts (`store.readPicture` asks the desktop adapter's `readAssetChecked` and rejects with its `reason`), and a dropped or pasted one over 150 megapixels is refused before anything is copied; the Boards list draws a page of cards and loads a card's pictures only while it is in view (`PreviewUrls`); a closed view does nothing; the Boards view and the Projects board fill the window, so the 3D view behind them is not drawn while they are up (`FULL_PANEL_VIEWS`, `BrainController.setCovered`, driven from the view by `App.tsx`) and their panel is solid. A board is open in one place at a time (docked or in the floating window), so two writers never meet. The floating window (`board.html`) never boots a vault and has the least bridge of any window: no `openVault`, `listFiles` or anything that restarts the watcher, a preload of its own that exposes only the board calls (`board-preload.cts`), and main answers its page no other channel (`BOARD_PAGE_CHANNELS`, `guardIpc`): that page decodes pictures from the user's folders, so a broken decoder must not be a way to read, change or delete the vault or any note. `board:read` and `board:save` are answered only for the one board the window shows, and `vault:reveal` only for a picture, a video or that board (`BoardWindowHost.pageRefusal`, applied by `guardIpc` to that page's messages alone); its saves (`board:save`) only overwrite that existing board note, and a close of the window is held (up to 1.5 s) while its page writes what it has not written. `BOARD_COMMANDS` (`board/commands.ts`) is the only table of the board's commands and keys: the palette, the cheatsheet, the menus and the key map are read from it and tests keep docs/KEYBOARD.md and docs/REFERENCE-BOARD.md in step; a new board command needs a row, a place in `COMMAND_HOME` (`board/view/menus.ts`) and a line in both docs. While the Boards view is up the global key handler ignores every single key but `?`, `/` and `2`–`7` (and `8`, `⇧ B`: up), and a test presses all of them: the board's letters are the 3D view's letters.
- Anything drawn per frame lives in `BrainScene.tsx` and reads from refs/typed arrays — no React state on the hot path.
- Colors: `packages/graph/src/theme.ts` and the `:root` tokens in `packages/ui/src/styles.css` must agree.
- Tests live next to the package (`packages/*/test`, `apps/desktop/test`). Add a test when you touch parsing, resolution, search, folders, projects or store actions.
- **Tests run the same on a Windows checkout** (the Windows job gates on them: `desktop.yml` checks each command's exit code, because pwsh does not stop at a failure). Four things made them fail there, so: a test that searches a repo file's text (a snippet of `main.ts`, a heading of a doc) reads it through `lf` (`apps/desktop/test/lf.ts`, `packages/ui/test/helpers/lf.ts`), since Git for Windows checks out CRLF; never `new URL(…).pathname` for a path (`fileURLToPath`), and never `pathToFileURL` of a POSIX path judged as `'linux'` without `{ windows: false }`; and vitest runs in UTC (`vitest.config.ts`), so a date made from a timestamp is the same everywhere. `lf` is for repo text to be searched only: tests of what a writer does with line endings read their own temp files as they are.
